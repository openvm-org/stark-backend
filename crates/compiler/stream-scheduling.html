Stream & Memory Co-Scheduling

How the compiler decides what runs when, on which GPU stream, and where each buffer lives in memory — all at once. Written for engineers comfortable with GPUs but not necessarily with compiler internals.

1. The setting

The compiler lowers a mathematical program into a directed acyclic graph (DAG) of kernels. Each node is one launch: a GPU kernel, a memory copy, or a memset. Edges express data dependencies — node v reads a buffer that node u writes, so u must finish before v starts.

Today the runtime issues every launch onto a single CUDA stream, in a topological order that also minimises peak memory. That's safe and simple, but it leaves two forms of concurrency on the table:

  • Kernel-level: two independent kernels could run on different streams and overlap on the GPU.
  • Copy/compute overlap: a host-to-device copy on one stream can hide behind a kernel on another.

Turning that concurrency on isn't free. Two kernels running at the same time also need their input and output buffers resident at the same time. If the device is memory-constrained (large workloads, small GPUs), naively parallelising the schedule can push peak memory past the budget and OOM. So the question is joint: choose an order, a stream per node, and a memory offset per buffer that together minimise wall-clock time subject to a memory cap.

The problem has three knobs, one per axis of the trade-off:
  • max_concurrency — how many streams the scheduler may use.
  • max_memory — the byte cap on the shared device pool.
  • Look-ahead depth k and beam width b — how hard the scheduler is allowed to think before committing to each pick.

2. A worked example

Consider five nodes with different runtimes and different output-buffer sizes (in some notional MB):

NodeReadsWritesOutput sizeRuntime
N1 load A—A40010 ms
N2 load B—B502 ms
N3 transform AAC20030 ms
N4 transform BBD505 ms
N5 mergeC, DE1008 ms
Figure 1 — a small compute DAG. Two independent loads feed two transforms; both feed a merge.

What single-stream does

Runs everyone sequentially: N1 → N2 → N3 → N4 → N5. Wall-clock is 10 + 2 + 30 + 5 + 8 = 55 ms. Peak memory is bounded by whatever's alive at once — with careful ordering, only A + C ever coexist, so about 600 MB.

What two-stream with unlimited memory does

Figure 2 — two-stream schedule with 2 streams and no memory cap. Makespan drops to 54 ms; the critical path is N1 → N3 → N5.

Peak memory in that schedule is roughly A(400) + B(50) + C(200) + D(50) = 700 MB — all four buffers coexist briefly.

What happens with a 500 MB cap

Now the concurrency we just bought is illegal: running the two branches in parallel would push us above 500 MB. The scheduler has to choose between several imperfect options:

  • Serialise the branches. Do N1 → N3, freeing A before starting the B branch. Wall-clock 55 ms.
  • Interleave. N1 on stream 0 while N2 runs on stream 1 (fits: 450 MB). N4 finishes early; hold N3 until B and D are dead; then N3 fits alone. Better than pure serial, still worse than the unbounded-memory schedule.
  • Reorder. Notice that starting N3 earlier dominates makespan, so pushing N2/N4 later is fine — they hide behind N3's 30 ms anyway.

Picking the right compromise is exactly the co-scheduling problem. Even on this five-node graph, the answer changes depending on the memory cap and stream count. On a real graph with hundreds of kernels, hand-tuning is not an option — the scheduler has to do it.

3. High-level ideas in the V1 scheduler

3.1 Score each ready node with a critical-path heuristic

At any moment, some nodes are ready — all their predecessors have been scheduled. The scheduler needs a way to pick "the best" one. It uses the bottom level, a classic list-scheduling heuristic: 

bl(v) = runtime(v) + max over successors u of bl(u)

bl(v) is the longest weighted path from v to any sink. Intuitively: if we delay this node, how much do we delay the whole program in the worst case? High-bl nodes go first because they sit on the critical path.

3.2 Add pressure terms for memory and stream idleness

Bottom-level alone doesn't know about memory. The full step score adds two more terms: 

score(v) = w_cp   · (bl(v) + est_finish(v))
         + w_mem  · max(0, live_bytes_after_v − 0.9 · max_memory)

The first term still pushes the critical path. The second term only kicks in once the pool is 90% full — a soft "you're running out of room" penalty that biases the scheduler toward nodes whose outputs are small or whose inputs die immediately, freeing space.

3.3 Look ahead a few picks before committing

Pure greedy scheduling gets stuck. Example: a small-output node scores well right now, but taking it starves a large-output node that then can't fit later. V1 avoids that with beam search:

  1. Score every ready node. Take the top beam candidates (typically 2–4).
  2. For each candidate, snapshot the scheduler state, tentatively place it, and recurse for k more picks.
  3. Score the leaf state by simulated makespan + a small memory penalty.
  4. Commit only the first move of the best rollout. Then re-plan from the new state.

The cost is O(beamk · score_cost) per decision. With k = 3, beam = 2 that's 8× a greedy pick — cheap for graphs with <1000 nodes.

3.4 Best-fit memory placement, with an offline repack at the end

When a node is committed, its output buffers each need a byte offset in the pool. The online allocator does a best-fit search: sort the currently-live intervals by offset, sweep the gaps, and pick the smallest gap that fits. Alignment is honoured by rounding the candidate offset up.

Online best-fit is fast but shortsighted — it doesn't know what's coming. Once the schedule is fixed, V1 runs an offline best-fit-decreasing (BFD) repack over the wall-clock lifetime intervals: sort all buffers by size (largest first), place each at the smallest aligned offset that avoids every already-placed lifetime-overlapping buffer. This is the same trick the single-stream heuristic backend uses, adapted to continuous-time intervals so it works for multi-stream plans.

3.5 Cross-stream synchronization via events

If node v reads a buffer produced by u and the two ended up on different streams, the runtime needs a wait. V1 emits this by having u record a CUDA event, and inserting a WaitOn(v's stream, event) instruction into the plan before v's launch. Repeated waits on the same event are de-duplicated. Nodes with no cross-stream consumers record no event, keeping event count small.

The output of the scheduler is a single flat list of instructions: 
enum StreamInstr {
    Node(usize),           // launch node k on stream[k]
    WaitOn(stream, event), // stream waits for event to fire
}
Plus one Option<offset> per buffer. The runtime just walks the list.

4. Formalizing the optimization problem

Let $G = (V, E)$ be the DAG. Each node $v \in V$ has an estimated runtime $r_v \in \mathbb{R}_{\ge 0}$. Each buffer $b \in B$ has size $s_b \in \mathbb{Z}_{>0}$ and alignment $\alpha_b$. The set of buffers read by node $v$ is $R(v) \subseteq B$; the set written is $W(v) \subseteq B$.

Decision variables.

  • $t_v \in \mathbb{R}_{\ge 0}$ — start time of node $v$.
  • $\sigma_v \in \{0, 1, \dots, M-1\}$ — stream assignment, where $M$ is max_concurrency.
  • $o_b \in \{0, 1, \dots, C-1\}$ — byte offset of buffer $b$ in the device pool, where $C$ is max_memory.

Derived quantities.

The birth and death of a buffer $b$ come from the nodes that touch it:

$$ \mathrm{birth}(b) \;=\; \min_{u \in \mathrm{writers}(b)} t_u, \qquad \mathrm{death}(b) \;=\; \max_{v \in \mathrm{writers}(b) \cup \mathrm{readers}(b)} \bigl(t_v + r_v\bigr). $$

Two buffers $b_1, b_2$ have overlapping lifetimes iff $\mathrm{birth}(b_1) < \mathrm{death}(b_2)$ and $\mathrm{birth}(b_2) < \mathrm{death}(b_1)$.

Constraints.

(C1) Precedence. For every edge $(u, v) \in E$, $$ t_v \;\ge\; t_u + r_u. $$

(C2) Same-stream serialization. For every pair of distinct nodes $u, v$ with $\sigma_u = \sigma_v$, one must precede the other on the timeline: $$ t_u + r_u \le t_v \quad \lor \quad t_v + r_v \le t_u. $$

(C3) Memory disjointness. For every pair of buffers $b_1 \ne b_2$ with overlapping lifetimes, their byte ranges must not overlap: $$ o_{b_1} + s_{b_1} \le o_{b_2} \quad \lor \quad o_{b_2} + s_{b_2} \le o_{b_1}. $$

(C4) Alignment. $$ o_b \equiv 0 \pmod{\alpha_b}, \qquad \forall b \in B. $$

(C5) Memory budget. $$ o_b + s_b \;\le\; C, \qquad \forall b \in B. $$

Objective. Minimise the makespan $$ T \;=\; \max_{v \in V} \bigl( t_v + r_v \bigr), $$ optionally with a secondary penalty on the peak occupied memory $P = \max_b (o_b + s_b)$: $$ \min\; \alpha \cdot T \;+\; \beta \cdot P. $$

4.1 Why this is hard

This problem contains three NP-hard sub-problems as special cases:

  • Ignoring memory (drop (C3)–(C5)) collapses to the classic $P_M \mid \mathrm{prec}, r_j \mid C_{\max}$ job-shop scheduling problem — NP-hard for $M \ge 2$.
  • Fixing the schedule and asking only for offsets is dynamic storage allocation (DSA), also called interval graph colouring with bandwidth — NP-hard (Gergov, 1999).
  • The joint problem is at least as hard as either piece and adds coupling between them: the schedule determines the lifetime intervals, which determine feasibility of the offset packing.

So we can't expect an exact solver to scale. V1 attacks it with a beam-search list scheduler for $(t_v, \sigma_v)$ and best-fit + offline BFD repack for $o_b$ — a decoupling that trades optimality for compile-time predictability.

4.2 Bounds and quality signals

Two easy lower bounds serve as sanity checks:

$$ T \;\ge\; \max_v \mathrm{bl}(v), \qquad T \;\ge\; \frac{1}{M} \sum_{v \in V} r_v. $$

The first is the critical-path length under infinite concurrency; the second is the sum of runtimes divided by the number of streams (work / machines). If the scheduler's returned $T$ is close to either bound, there's not much optimization headroom left.

5. What V1 does not do

  • No spilling to host memory. If the graph can't fit at any legal schedule, the compiler errors — it won't insert a device-to-host swap.
  • No reordering of committed nodes. Look-ahead is the only backtracking mechanism; there's no post-hoc local search / kernel swap.
  • No partial-overlap analysis on Memcpy source/destination ranges — a memcpy is treated as reading its src and writing its dst, atomically.
  • No event coalescing beyond de-duplication at plan time — multiple consumers of the same producer on the same stream will still share a single WaitOn, but consumers on different streams each wait individually.
